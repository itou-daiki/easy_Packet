## 1. コンテキスト概要

### 何を作っているのか

山梨大学「情報ネットワーク演習」の授業で、生徒が `nslookup` / `ping` / `traceroute` /
`ipconfig` を打ちながらネットワークの仕組みを体感するための Web 教材。
バックエンドを持たない静的サイトで、GitHub Pages で公開されている。

### 今どうなっているのか

構成は 2,432 行。フレームワークなし、ビルドなし、テストなし。

```
index.html          画面（3カラム: チュートリアル / 図＋コンソール / コマンド＋用語集）
command-guide.html  コマンド解説ページ（インラインCSS 148行）
style.css           スタイル 587行
simulator.js        コマンド解釈と結果生成 465行  ← 外部API依存
visualizer.js       canvas 描画とアニメーション 452行  ← サイズ計算が破綻
app.js              画面とロジックの接続 199行  ← 実行制御が脆い
dns.json            ドメイン→IP の対応表（10件）  ← ほぼ使われていない
routes.json         traceroute 用の経路表（5件）  ← ほぼ使われていない
```

### 何が壊れているのか（詳細は調査レポート）

**致命的なもの3件**

- **F-1** `visualizer.js:15-35` が canvas 自身の実測幅から `canvas.width` を決めているため、
  resize のたびにサイズが倍増する（実測: 1600 → 3200 → 6400 → 12800 → 25600 px）。
  図が横に2倍歪み、レイアウトが破綻し、`body{overflow:hidden}` と相まって入力欄とボタンに
  到達できなくなる。
- **F-2** 仕様書は「完全な静的サイト・実際のネットワークにパケットを送信しない」と書いているのに、
  実装は `dns.google` / `ipapi.co` / `api.ipify.org` を呼んでいる。外部通信を遮断すると
  **4コマンドすべてがエラー**になる。`dns.json` / `routes.json` は読み込まれているのに使われない。
- **F-13** `app.js` の `executeCommand()` に try/finally がなく、描画で例外が出ると
  `isExecuting` が true のまま残り、**コンソールが永久にロックされる**。

**高**: F-3 目的地ノードが画面外 / F-4 実行後6.3秒の無反応 / F-14 失敗しても成功アニメーションが流れる /
F-15 アイドル時も描画し続ける

**中〜低**: F-5, F-7〜F-12, F-16〜F-20（アクセシビリティ、未使用CDN、説明文の矛盾ほか）

### 改修後にどうなっていてほしいか

1. どんなネットワーク環境でも、`file://` で開いても、4コマンドすべてが動く
2. 画面をどうリサイズしても図が歪まず、目的地ノードが必ず見える
3. コマンドを打った瞬間から反応があり、コンソールの行とパケットの動きが同期している
4. エラーのときはエラーのアニメーションになる（成功に見えない）
5. 教える情報に事実誤りがない
6. キーボードだけで操作でき、スクリーンリーダーでも内容が分かる

## 2. 設計方針

### 2-1. データソースの方針 ★要承認

**推奨: 「オフライン既定 ＋ ライブ任意」の二層構造**

| モード | 動作 | 既定 |
|---|---|---|
| オフライン | `dns.json` / `routes.json` のみを参照。外部通信ゼロ | ● |
| ライブ | 実際の DNS-over-HTTPS を引く。失敗したら自動でオフラインに落ちる | 画面のトグル or `--live` フラグ |

理由:

- 仕様書（`CLAUDE.md`）自身が「安全性」「安定性」「いつでも同じ結果を再現」を掲げている
- 授業は**再現性が命**。全員が同じ結果を見られないと進行できない
- `ipapi.co` の無料枠は 1,000req/日・IP単位。教室は NAT で全員同一IPのため1クラスで枯渇する
  （調査時点で実際に HTTP 429 を受領済み）
- 一方で「本物のIPを見たい」という教育的価値も本物なので、捨てずに任意機能として残す

> **この方針だけは実装前に伊藤先生の承認を取ること。** 「完全オフラインにする」「ライブ優先のまま直す」
> のいずれかを選ばれた場合は、Phase 3 のタスクを差し替える。他のフェーズは方針に依存しない。

### 2-2. リファクタの範囲

**フレームワーク導入・ビルドツール導入はしない。** 素の HTML/CSS/JS のまま直す。

理由: GitHub Pages にそのまま置ける手軽さが本プロジェクトの価値であり、
授業担当者が中身を読んで直せることが重要なため。

ただし以下の分割は行う（1ファイル1責務にして再発を防ぐ）。

```
js/
  data.js        dns.json/routes.json の埋め込みデータと読み込み
  simulator.js   コマンド解釈（副作用なし・純粋に結果を返す）
  visualizer.js  canvas 描画（サイズ管理を1箇所に集約）
  console.js     コンソールDOM（textContent のみ）
  app.js         接続と実行制御
tests/
  *.test.mjs     node --test で回す
```

## 4. 進め方（Claude ↔ Antigravity の往復）

1. **Antigravity**: フェーズ着手前に、そのフェーズの実行計画（変更するファイルと方針）を提示する
2. **伊藤先生**: 承認する
3. **Antigravity**: 実装する。1フェーズ＝1コミット
4. **Antigravity**: 「検証」のチェック項目を**実測**で埋め、スクリーンショットとともに報告する
5. **Claude**: 差分と実測値をレビューし、漏れ・副作用・再発リスクを指摘する
6. 指摘があれば 3 に戻る。なければ次のフェーズへ

### 並行してよいもの / いけないもの

- **Phase 1 は単独で先行させる。** 他のフェーズは canvas サイズが安定していることを前提にしている
- Phase 2 と Phase 3 は並行可（触るファイルが別）
- Phase 4 は Phase 2 の完了が前提（実行制御の上に載るため）
- Phase 5 は Phase 1 の完了が前提
- Phase 6 / 7 / 8 は互いに独立、並行可
- Phase 9 は最後

### 着手順の推奨

```
Phase 0 ──► Phase 1 ──┬──► Phase 2 ──► Phase 4 ──┐
                      ├──► Phase 3 ──────────────┤
                      └──► Phase 5 ──────────────┼──► Phase 9
                           Phase 6 ──────────────┤
                           Phase 7 ──────────────┤
                           Phase 8 ──────────────┘
```

## 5. やらないこと（スコープ外）

- フレームワーク（React/Vue 等）への移行
- ビルドツール（Vite/webpack 等）の導入
- 実際に ICMP を送る機能（ブラウザでは不可能であり、教育上も不要）
- 新しいコマンドの追加（まず既存4つを確実に動かす）
- デザインの全面刷新（配色・レイアウトの骨格は維持する）
