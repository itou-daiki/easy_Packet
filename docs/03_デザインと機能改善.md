## 第1部 デザイン刷新

### いまのデザインが「AIっぽい」理由（計測結果）

感想ではなく、機械的に数えられる事実です。

| 指標 | 実測 | なぜ問題か |
|---|---|---|
| `linear-gradient(135deg, ...)` | **7箇所** | 135度・2色停止のグラデーションは生成UIの最大の指紋。とくに `#667eea → #5568d3` はネット上で最も多く生成された配色の組み合わせ |
| 絵文字 | **96個**（index 26 / guide 42 / js 28） | 見出し・ボタン・コンソール出力・ノードラベルの全階層に散布。意味を持つものと装飾が混在している |
| 配色 | Tailwind v1 の既定値をそのまま | `#667eea` `#48bb78` `#ed8936` `#9f7aea` `#38b2ac` `#f56565`。設計された палitre ではなく「フレームワークの初期値」 |
| 本文フォント | `'Segoe UI', Tahoma, Geneva, Verdana` | Windows 専用フォント。学生が使う Mac・iPad では最初の指定が当たらず、意図しない書体に落ちる |

唯一 `#0071BC`（9箇所）だけが意図を感じる色です。これを起点に配色を組み直します。

### 方針：授業で使う道具として作り直す

これは90分間ずっと開いたままにする**作業用の道具**であって、ランディングページではありません。

| 捨てるもの | 採るもの |
|---|---|
| 7箇所のグラデーション | 単色。institutional blue `#0071BC` を基幹色に据える |
| 装飾的な絵文字 | 原則削除。ノードの種類など**意味を運ぶ記号だけ**残す |
| Tailwind 既定色の寄せ集め | `#0071BC` から導いた階調＋データ表示用の識別色を設計 |
| `'Segoe UI'` 単独指定 | `system-ui` を先頭に、日本語フォールバックを明示した実用スタック |
| 余白の多いカード基調 | 情報密度優先。1画面で「課題・図・コンソール」が同時に見える |
| 丸みと影の多用 | 図表としての明快さ。線と面で構造を示す |

### 具体的にやること

1. **色をトークン化する**（`:root` の CSS 変数に集約）。現在32種の生の色コードが CSS に直書きされている状態を解消
2. **グラデーション7箇所を単色に置換**
3. **絵文字の棚卸し** — 見出しの装飾絵文字は全廃。ノードのアイコンは「PC / ルータ / DNS / サーバ」を区別する記号として残すが、絵文字ではなく**図形で描く**（canvas なので描ける）
4. **フォントスタックを実用的に** — `system-ui, -apple-system, "Hiragino Sans", "Noto Sans JP", sans-serif`。コンソールは `ui-monospace, "SF Mono", Consolas, "Noto Sans Mono", monospace`
5. **コンソールを主役にする** — いまは canvas と同じ高さで並んでいるが、生徒が最も長く見るのはコンソール。配分を見直す
6. **模式図を「技術図」にする** — 色とりどりの丸ではなく、機器の種別が形で分かる図に
7. **コントラスト基準を満たす**（旧 Phase 6 から統合。接続線 1.34、ホスト名 3.63、プレースホルダ 3.72 が現状 NG）

## 第2部 目的を達成するための機能改善

### 根本的な問題：`easyPacket` という名前なのに、パケットが無い

このアプリの学習目標は仕様書にこう書かれています。

> 「パケットという主役が、IPアドレスという住所を頼りに、ルーターを経由して旅をする」という、ネットワークの根幹をなす仕組みの理解に集中できます。

ところが現在の実装では、**パケットは色のついた丸**でしかありません。中身も、宛先も、TTL も見えない。主役が居ないのです。

### 仕様書が約束していて、作られていない機能

調査で判明した「書いてあるのに無い」もの。

| 仕様書の記述 | 実装状況 |
|---|---|
| 「Webサイトが表示されない！」といったシナリオ形式の演習課題 | **未実装**。チュートリアルは「コマンドを試そう」のみ |
| 用語集をクリックすると解説が表示される | **未実装**。静的なテキストが並んでいるだけ |
| コンソール出力内の専門用語にマウスを合わせると解説 | `ttl=` のみ。他は無し |
| `broken-server.com`（`dns.json` に TIMEOUT として定義） | **どこからも参照されていない**。失敗シナリオが設計されたが作られなかった |
| Codemirror によるインタラクティブ・コンソール | 素の `<textarea>`。CDN だけ読み込んで未使用 |

### 改善案（教育効果の高い順）

#### ◎ I-1 パケットの中身を見せる ── 最優先

パケットを丸ではなく、**ヘッダを持つ箱**として描く。

```
┌── パケット ──────────────┐
│ 送信元  192.0.2.10       │
│ 宛先    203.0.113.50     │
│ TTL     64               │
│ データ  こんにちは        │
└──────────────────────────┘
```

そして **ホップを1つ越えるたびに TTL が減る様子を目で見せる**（64 → 63 → 62 …）。

これ1つで次がすべて解決します。

- アプリ名どおり「パケットが主役」になる
- 用語集にしかなかった TTL が**体験できる知識**になる
- **traceroute の仕組みが自明になる**（内容点検 C-5「核心が教材のどこにも書かれていない」の根本解決）
- 「IPアドレスという住所を頼りに旅をする」が文字どおり見える

#### ◎ I-2 traceroute を「本物の仕組み」で動かす

いまの traceroute は経路を順に描くだけです。そうではなく、実際の仕組みどおりに動かします。

```
TTL=1 で送信 → 1つ目のルータで寿命切れ → 「時間超過」が返る → 1ホップ目が判明
TTL=2 で送信 → 2つ目のルータで寿命切れ → 「時間超過」が返る → 2ホップ目が判明
TTL=3 で送信 → … 宛先に到達 → 完了
```

図の上でパケットが**毎回 PC から出発して、少しずつ遠くで力尽きる**。この絵を見れば、traceroute が何をしているか説明不要で分かります。

教材としての価値が最も高く、かつ現在の最大の内容欠落（C-5）を埋める改善です。

#### ○ I-3 失敗を体験させる

現状、すべてのコマンドが必ず成功します。ネットワークの学習で**切り分けの力**を育てるには、失敗こそ教材です。

- `broken-server.com` — 名前解決はできるが応答が返らない（既に `dns.json` に用意済み・未使用）
- 存在しないドメイン — 名前解決の段階で失敗する
- パケットロス — 4発中1発落ちる
- TTL 枯渇 — 経路がループして 30 ホップ上限に達する

**「名前解決で失敗したのか」「到達できないのか」「途中で止まっているのか」を切り分ける**——これが実務の技術そのものです。

#### ○ I-4 シナリオ演習を実装する（仕様書の約束）

> 「Webサイトが表示されない！」といったシナリオ形式の演習課題

課題を出し、生徒がコマンドで切り分け、原因に辿り着く。たとえば：

```
【状況】example-school.ac.jp が見られません。原因を突き止めてください。
  ヒント: まず名前解決ができているか確かめましょう
  → nslookup で確認  → ping で到達確認  → traceroute でどこで止まるか
【解答】ISP のルータより先で経路が途切れている
```

チュートリアル欄を「コマンド紹介」から「課題」に変えるだけで、アプリの性格が**体験する教材**に変わります。

#### ○ I-5 2つの経路を並べて比べる

国内（`yahoo.co.jp`）と海外（`google.com`）の traceroute を並べて表示する。ホップ数と往復時間の差が一目で分かり、**距離と遅延の関係**が体感できます。「なぜ海外のサイトは遅いのか」に答えが出ます。

#### △ I-6 用語をクリックできるようにする（仕様書の約束）

コンソール出力中の `TTL` `ICMP` `ホップ` などをクリックすると、右の用語集の該当項目が開く。仕様書にある機能で、実装コストも小さいです。

#### △ I-7 実行ログの書き出し

授業レポート用に、その時間に実行したコマンドと結果をテキストで保存できるようにする。
