# easyPacket 教材内容の点検（ネットワーク技術としての正確性）

- 点検日: 2026-09-18
- 対象: `dns.json` / `routes.json` / `command-guide.html` / `index.html` / `simulator.js`
- 方法: ソースの静的解析（`grep` による参照追跡）＋ **実際の DNS 問い合わせ（`dig`）と `whois` による裏取り**

## C-1 【高】`google.com → 8.8.8.8` は誤り。しかも教材内で自己矛盾している

### 裏取り

```
$ dig +short -x 8.8.8.8
dns.google.
```

**8.8.8.8 の逆引きは `dns.google`** です。これは Google Public DNS の**リゾルバ**であって、google.com の Web サーバではありません。

### 教材内の矛盾

| 箇所 | 記述 |
|---|---|
| `dns.json:2` | `"google.com": "8.8.8.8"` ← google.com 本体として扱っている |
| `routes.json:6` | `{ "ip": "8.8.8.8", "name": "google-dns.com" }` ← google.com 経路の**最終ホップ** |
| `command-guide.html:214-215` | 「`ping 8.8.8.8` ※ 8.8.8.8 は**Googleの公開DNSサーバー**のIPアドレスです」← **正しい** |

同じアプリの中で、ガイドは正しく「DNSサーバー」と教えながら、データ側は「google.com そのもの」として扱っています。

### 教育上の問題

「パブリックDNSリゾルバのIP＝そのサービス本体のIP」という典型的な誤概念を植え付けます。`nslookup` は**まさにその区別を教えるためのコマンド**なので、教材の中心部分で逆のことを教えていることになります。

### 直し方

- `dns.json` の google.com を実在の Web フロントエンドIP（例: `142.251.x.x` 系）に置き換える。あるいは架空のままにするなら RFC 5737 の例示アドレスにする
- `routes.json:6` の `"name": "google-dns.com"` を実際の呼称 `dns.google` に合わせる（現在の綴りは実在しないホスト名）

## C-2 【高】ランダム生成IPが 99.4% の確率で実在組織のアドレスになる

### 該当

`simulator.js:260` と `simulator.js:280`

```js
ip: `${Math.floor(Math.random()*220)+1}.${Math.floor(Math.random()*255)}.${Math.floor(Math.random()*255)}.1`
```

第1オクテット 1〜220、第2・3オクテット 0〜254 の**全域**から選んでおり、予約領域の除外が一切ありません。

### 網羅計算の結果

| 項目 | 値 |
|---|---|
| 生成されうる全組み合わせ | 14,305,500 通り |
| 予約領域（RFC 1918 / 5737 / 6598 等）に収まるもの | 86,193 通り（0.60%） |
| **実配当空間に落ちるもの** | **14,219,307 通り（99.40%）** |
| traceroute 1回で2箇所使うため、少なくとも一方が実アドレスになる確率 | **99.9964%** |

つまり **traceroute を実行するたび、ほぼ確実に実在する第三者のグローバルIPを「架空のバックボーンルータ」として生徒に見せています。**

### 直し方

ダミーIPの生成範囲を RFC 5737（`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`）に限定する。ランダム生成自体をやめて固定表にするのが望ましい（再現性の観点からも）。

なお同じファイルの `simulator.js:228` は `203.0.113.10` を使っており、**これが正しい書き方の模範**です。

## C-3 【高】実在組織のアドレスを「架空ルータ」として使っている

`whois` で実照会した結果です。

| 該当 | IP | 名乗り | **whois の実際の登録** |
|---|---|---|---|
| `simulator.js:245` | `198.32.176.1` | `international-ix.net` | **NET-PAIX-V4 / Equinix, Inc. (US)** — 実在のインターネットエクスチェンジ（PAIX）の運用ブロック |
| `routes.json:22` | `210.81.153.1` | `jp-backbone.net` | **VzB-JP-NETBLOCK / Verizon Japan Limited** — 実在の日本の通信事業者に割当済み |

参考（正しく使えている例）:

| `routes.json:5` 他 | `203.0.113.5` | — | 組織登録なし＝**RFC 5737 TEST-NET-3。正しい使い方** |

`198.32.176.1` は実在のIXの運用アドレスに酷似しており、「architecture上これは架空です」という教材の前提と正面から矛盾します。

### 直し方

両方とも RFC 5737 の3ブロックのいずれかに置き換える。

## C-4 【中】RFC 6598（CGNAT共有空間）を「バックボーン」「Azureエッジ」として誤用

`whois` 照会結果:

```
100.64.0.1 → NetRange: 100.64.0.0 - 100.127.255.255
             NetName : SHARED-ADDRESS-SPACE-RFC6598-IANA-RESERVED
```

| 該当 | IP | 名乗り | 実際の用途 |
|---|---|---|---|
| `routes.json:11` | `100.64.0.1` | `backbone-router.net` | ISPと加入者宅内機器の間の**キャリアグレードNAT専用** |
| `routes.json:28` | `100.65.0.1` | `azure-edge.net` | 同上 |

`100.64.0.0/10` がインターネットのバックボーンや Azure のエッジで使われることは**技術的にありえません**。アドレス空間の用途とホップ名が矛盾しています。

### 直し方

バックボーン／CDNエッジの例示は RFC 5737 に置き換える。`100.64.0.0/10` を使うなら「ISPの共有NAT機器」という**正しい文脈**のホップ名にする（それ自体は良い教材になります）。

## C-5 【中】traceroute の核心（TTLを1ずつ増やす仕組み）がどこにも書かれていない

### 該当

`command-guide.html:243-289`（traceroute セクション全体）、`index.html:168-171`（TTL用語集）

用語集の TTL 説明は「パケットが経由できるルーターの最大数。無限ループを防ぐ。」という **ping 文脈の説明のみ**です。

traceroute が「送信パケットの TTL を 1, 2, 3… と意図的に増やしながら送り、TTL が 0 になった中継ルータが返す **ICMP Time Exceeded** を利用して経路を1ホップずつ発見する」という**最大の技術的核心**が、教材のどこにも存在しません。

### 教育上の問題

本アプリの学習目標に「traceroute 等の基本コマンドの役割と使い方を習得する」と掲げられているのに、その核心が書かれていません。生徒は「経路情報をどこかから取得して表示しているだけ」という誤った理解のまま終わります。

### 直し方

- traceroute の解説に TTL 操作とICMP Time Exceeded の仕組みを追加する
- TTL 用語集から traceroute の項目へ相互参照を張る
- 本アプリの経路は**推定生成**であることを明示したうえで、「本来はこう動く」を併記する

## C-6 【中】OS表記が混在している

| 出力 | 該当 | 様式 |
|---|---|---|
| `ping` | `simulator.js:73,82` — `PING domain (ip): 56 data bytes` / `64 bytes from ip: icmp_seq=0 ttl=N time=N ms` | **macOS/BSD 系** |
| `ipconfig` | `simulator.js:314,318-320` — `Windows IP Configuration` / `IPv4 Address:` | **Windows 専用** |

同じ仮想PCの中で、ping は macOS 風・ipconfig は Windows 風という**矛盾したOS人格**になっています。

さらに `simulator.js:440-443` では、Mac/Linux のコマンドである `ifconfig` や、まったく別物の `whoami` を打っても**同じ「Windows IP Configuration」**が返ります。`command-guide.html:345-357` は「Mac の場合は ifconfig」と正しく教えているのに、アプリ内で `ifconfig` と打つと Windows の画面が出ます。

### 直し方

シミュレートするOSを1つに決めて統一する。「OSごとにコマンド名と出力が違う」ことこそ大事な学びなので、むしろ**OSを切り替えられる**ようにして、`ipconfig` と `ifconfig` で正しく出し分けるのが教材としては理想的です。

## C-8 【低】ping が常に成功し、パケットロスを学べない

`simulator.js:76-88` は必ず4発とも成功し、`0% packet loss` で固定です。

応答時間 15.0〜50.0ms、TTL 54〜63 という範囲自体は妥当ですが（初期TTL=64 から 1〜10 ホップ経由した場合と整合）、**パケットロスという重要概念に触れる機会がありません**。`broken-server.com` に TIMEOUT が用意されているので、部分的なロスのシナリオも足せます。

```

```

**この不一致自体は必ずしも誤りではありません。** 大手サイトは CDN と GeoDNS を使っており、応答は地域と時刻で変わるのが正常です。教材として固定値を持つこと自体は再現性の観点でむしろ正しい判断です。

ただし **C-1 の 8.8.8.8 だけは種類の違う誤り**です。「古い値」でも「別リージョンの値」でもなく、**そもそも Web サーバではないもの**を Web サーバとして教えています。

対応方針としては、固定値を持つこと自体は維持したうえで:
- 8.8.8.8 を正しい値に差し替える
- 画面に「この値は授業用の固定データです。実際のIPは時期や地域で変わります」と明示する（これ自体が CDN と GeoDNS を教える良い教材になります）

## 参考：dns.json / routes.json は実際どれだけ使われているか

`grep` で全参照を追跡した結果です。

### `this.dnsData`（dns.json）— **完全な死にデータ**

```
simulator.js:4   this.dnsData = {};              ← 初期化
simulator.js:15  this.dnsData = await ...json(); ← 代入
```

**代入の2箇所のみ。読み出しが1箇所もありません。**
（107・109・114・172・174・178行の `dnsData` は `this.` の付かない別のローカル変数で、DoH の応答です）

### `this.routesData`（routes.json）— アニメーション用にのみ生存

```
app.js:131,132        ping のアニメーション経路として（コンソール出力には効かない）
simulator.js:139      到達不能なフォールバック（F-2 参照）
```

つまり **routes.json は「図の中のパケットがどこを通るか」にしか効いておらず、コンソールに表示される経路とは無関係**です。図とコンソールが別々のデータ源を持っているため、両者が食い違います。
